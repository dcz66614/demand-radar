## R1-A — API Reliability Validator (AI 6513d0)

`mvps/r1_a/validator.py` + `make_fixtures.py` + `data/fixtures.json`
(14 scenarios, 21 checks, every scenario carries its `source_url`) +
`app.py` + `README.md`.

- Simulated transport, deterministic virtual clock, no network, no paid
  calls. Retry budget max 3 attempts, 60 s simulated per timeout attempt
  (AgentLab #182); the budget is never exceeded (tested).
- Outcomes: ok / timeout / rate-limited / server-error / wrong-result /
  default-substituted / token-budget. `server-error` (HTTP 500) and
  `token-budget` extend the brief's five, because a 500 is neither a wrong
  result nor a timeout and a budget failure must not be lumped with wrong
  results — recorded here, not hidden.
- #340 tokenizer check: reported counts are validated against the named
  model's tokenizer within the PRD's 2% tolerance; a count matching the
  GPT-4 counter is `default-substituted`. The two counters are small
  deterministic approximations (CJK ideograph 2 tokens under GPT-4 vs 1
  under the named model; long English words split in two under GPT-4 only;
  code identical), reproducing the direction/magnitude of the measured
  errors — fixture overcounts: Chinese +91.7% (measured +108.3%), English
  +10.5% (+11.7%), Japanese +21.2% (+18.5%), code 0% (0%). They are NOT the
  real tokenizers; detection is the product.
- #41708 streaming: correct handler emits exactly one completed chunk on
  `done`; the buggy handler emits none and is flagged; no `done` means no
  chunk may be emitted.
- HN #50382039: a false OpenRouter response after a 45 s wait is classified
  `wrong-result` with the latency recorded, never returned as success.
- Results on fixtures: 8 pass, 13 fail — the 13 "fail" rows are injected
  faults correctly *detected*, not MVP defects. Every row carries source_url.
- UI: kind + outcome filters, CSV export with source_url, uploaded scenario
  JSON validated (malformed files rejected with an error, not a crash).

Tests: `mvps/r1_a/tests/test_validator.py` (24) + `test_app_r1a.py` (3
AppTest UI-flow tests: run + result view, outcome filter -> 13 fail rows,

## What each MVP does and does not prove

- Both MVPs prove *detection* of the PRD's recorded failure classes on
  recorded reproducers, with pass/fail, measured vs expected values, and
  source links. Neither fixes the upstream library, neither calls a real
  API or a real signal-processing library, and neither is described as a
  fixed API/signal product anywhere in code, UI or docs.
- R1-A's tokenizers are approximations; a real deployment must plug in the
  actual per-model tokenizers and re-run the same 2% checks.
- R1-B's fixtures are synthetic; the validator checks the failure classes,
  not the original recordings. Three cited items (#1208, #1230, #1196) may
  already be fixed upstream — the MVP does not claim otherwise.
- No MVP is marked NOT_ACCEPTED: both address their PRD's cited examples
  on genuine fixtures (tokenizer substitution + streaming completion for
  R1-A; EMG filter rate + short-RSP crash for R1-B, both still-open issues).
  The "fail" rows in the fixture runs are the injected/recorded failures
  being caught, which is the intended behaviour.
