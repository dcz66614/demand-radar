# P2-A — chunk validity vs request completion (sixth-round audit P2-A)

Scope: the sixth-round independent audit of the POST-R4 delivery (verdict
POST_R4_SCOPE_ACCEPTED / ACCEPTED_RESEARCH_PROTOTYPE_ONLY, 2026-11-07)
left four non-blocking items. P2-A is the only one that is a code change:
an open stream could return `passed=True` (74/400 random OPEN streams in
the auditor's re-check), because `passed` checks chunk coherence, not
whether the request completed. The audit's prescription, implemented
here: split `call_chunk_valid` from `request_completed_successfully`,
set un-terminated streams to PENDING/INDETERMINATE, never count them in
the "complete request success" ratio, and count them separately in the
UI. This is a new stage, not another REWORK round — the auditor
recommended stopping the REWORK sequence, and production-grade
validation is a separate stage.

## 1. Design decision: `passed` does NOT change meaning

A frozen regression file pins the old semantics:
`tests/test_independent_r3.py:91`
(`test_legal_no_arguments_completed_function_call_still_passes`) asserts
an open stream (added + done, no terminal event) has
`validate_stream(...)['passed'] is True`. So `passed` keeps its
long-standing meaning — chunk coherence — and the split is additive:

- `call_chunk_valid` — identical to `passed` (chunk coherence: completed
  set == done set, no orphans, no anomalies, all arguments valid, not
  terminated-with-pending, no failure terminal).
- `request_completed_successfully` — `call_chunk_valid and termination ==
  "completed"`. Only a normally terminated, chunk-valid stream counts.
- `request_status` — `"completed"` / `"pending"` / `"failed"` /
  `"not-checked"`. `"pending"` iff termination is `"open"` and the chunks
  are coherent; `"failed"` for a failure terminal, terminated-with-pending
  or any chunk incoherence; `"not-checked"` only when no streaming events
  arrived at all (outcome `"not-checked"`).

No separate `request_status` enum beyond these four values was needed:
the triple (termination, call_chunk_valid, request_completed_successfully)
already expresses it, and the single field makes the classification
explicit for consumers. `outcome` is unchanged (`"ok"` /
`"wrong-result"` / `"not-checked"`).

## 2. P2A-01 — validator split (`mvps/r1_a/validator.py`)

- `validate_stream` returns the three new keys in both return paths
  (the no-events early return and the main return); docstring documents
  the split.
- `CallResult` gains three fields with defaults (backward compatible for
  all positional constructions): `termination: str = ""`,
  `request_completed_successfully: bool = False`,
  `request_status: str = ""`.
- New helper `_request_completion(outcome, passed) -> (bool, str)` for
  non-streaming checks: a request completed successfully iff its check
  outcome is `"ok"` and it passed; status `"completed"` then, `"failed"`
  for any other checked outcome, `"not-checked"` when the check never
  ran. Used by `run_step` (all three return paths) and the `token_count`
  branch of `run_scenario`. Non-streaming rows leave `termination` empty.
- The `streaming` branch of `run_scenario` threads the three fields from
  the `validate_stream` check dict.
- `export_csv` fieldnames gain the three new columns (this surfaced
  immediately: `asdict` includes them and DictWriter raised until the
  fieldnames were extended — one full-suite failure, fixed in the same
  step, not a design change).

Verified live: frozen 26/26, full suite 334/8, ruff clean, format clean.
Spot checks: open added-only stream → passed True, call_chunk_valid
True, rcs False, status pending, outcome ok; added+done+completed →
all True, status completed. Fixture sweep under the new counting:
**7 passed / 13 failed / 0 not checked / 2 pending** (the two pending
rows are streaming-completed-41708 and streaming-no-done — both open and
chunk-valid; the recorded #41708 replay has no terminal event).

## 3. P2A-02 — UI four-way counting (`mvps/r1_a/app.py`)

- `passed` now counts only `request_completed_successfully`; `pending`
  counts `request_status == "pending"`; `not_checked` and `failed`
  (len − passed − pending − not_checked) are unchanged in definition —
  verified: the failed count stays 13, so the four counts partition the
  22 checks.
- Outcome filter gains a `"pending"` option; the `"pass"` filter now
  selects `request_completed_successfully` (consistent with the new
  counting); the `"fail"` filter is unchanged.
- Summary line: "**7 passed, 13 failed, 0 not checked, 2 pending** of
  22 checks".
- Banner: an open stream is now described as counted as **pending**
  ("a pending result is not a completed success and never counts toward
  the pass total"); the failure-terminal sentence is unchanged.
- Result table gains `termination` and `request_status` columns (a
  pending row still shows passed=True on chunk coherence, so the status
  column is what makes it self-explanatory).
- The app's own CSV writer (separate from `export_csv`) gains the three
  new columns.

## 4. What did NOT change

- No fixture changed; no frozen test changed; no research conclusion
  changed (gate 0/221, fingerprint unchanged — re-verified in the
  clean room).
- `passed` / `outcome` / `termination` semantics are byte-for-byte the
  POST-R4 semantics; only additive fields and the UI counting changed.
