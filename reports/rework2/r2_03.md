## 1. Method

- **Scope:** every `evidence_links` row of the 5 REWORK1-qualifying
  themes — 76 links (6 + 19 + 19 + 16 + 16). All 76 were assessed;
  0 UNKNOWN.
- **Body basis:** the full issue body of each link, as collected live
  in R02 (`reports/rework1/review_r02_raw_github.json`,
  `review_r02_raw_hn.json`, 2026-11-05). Load-bearing issues were
  re-read live on 2026-11-06: NeuroKit #1176, #1236; wfdb #538;
  MNE #14321; edgartools #1848; OpenBB #7744; yfinance #3012;
  langchain #41708. Titles and bodies matched the R02 record in all
  9 live checks.
- **Granularity rule (one signature per theme):** the signature is
  written at the level of the R05 PRD's own sample input / acceptance
  tests — the user operation, the failure class, and the expected
  output. It is NOT the broad domain ("reliability", "finance") and
  NOT one function/bug at a time: different functions exhibiting the
  same user-visible failure class on the same operation are the same
  problem; a different operation (file loading vs signal computation,
  model loading vs API-call result), a different failure class (loud
  timeout vs silent wrong result), or a non-failure (feature request,
  packaging, docs, CVE tracking, vendor promotion) is not.
  - The brief's own mandatory split calibrates this: Docker/CAPTCHA/
    benchmark-reproduction are separated from "tokenizer/streaming"
    (treated as one side); docs CI / package management / setuptools
    pin are separated from "signal function computes wrong/crashes";
    13F positions / chart RFC / CVE are three different product
    problems.
  - `affected_product` in the signature names the product scope of the
    problem (e.g. NeuroKit2 for the core-algorithm theme). A link from
    a different product can be DIRECT only if its product is inside
    that scope AND every other field matches.
- **Classifications:** `DIRECT_SAME_PAIN` (reports the signature's
  problem), `ADJACENT_CONTEXT` (same workflow/domain, different
  operation/product/failure — background only), `DUPLICATE` (the same
  report filed more than once — later filings add nothing, however the
  first is classified), `OUT_OF_SCOPE` (a different problem),
  `UNKNOWN` (unreadable — never guessed; none occurred).
- **Duplicates vs independent reports of the same bug:** #522/#524
  (rdann OverflowError, different authors/datasets) and #543/#618
  (wrsamp TypeError, different authors) are independent reports of one
  underlying bug and both count. #41708/#41709/#41710, #41717/#41718,
  #3011/#3012, #7650/#7651 are the same report text by the same author
  and count once.
- **Closed != fixed (review §6):** `issue_state` below is the R02
  value (2026-11-05). Resolution was NOT checked from comments, so a
  CLOSED link is recorded as "closed, resolution unverified", never as
  "solved". Open/closed counts are given for the DIRECT sets only.
- **Reproducibility:** `reports/rework2/assess_r2_03.py` (signatures +
  76 classifications, idempotent upserts, asserts every link of the 5
  themes is assessed exactly once, exports the CSV from the DB).
  Code: `src/demand_radar/evidence_assessment.py`;
  migration: `src/demand_radar/db.py::init_db` (new tables
  `problem_signatures`, `evidence_assessment`; old data untouched).

## 2. Problem signatures

### 0b7a FIN — use a financial research tool
- actor: investor/researcher using a financial research tool to compare institutional holdings
- input_artifact: two 13F-HR filings for the same manager (Bank of America Q2/Q3 2024) with compare_holdings()/holding_history()
- operation: cross-match equity, Put and Call positions on the same CUSIP across periods
- observed_failure: position identity (Cusip, PutCall) is lost in the join: 10,878 rows instead of 8,753 union position keys; Value sums to ~2.10x the filed Q3 total; new option positions shown DECREASED instead of NEW
- expected_output: 8,753 union position keys with like-designation pairs; Value sums match the filed information-table totals; a missing position is flagged, never silently merged
- affected_product: edgartools (edgar.thirteenf)
- version_or_environment: edgartools upstream main @ 5ae0f6352, Python 3.13.17, pandas 3.1.0, Windows 11 Pro

### 4bb7 BIO — process physiological signals correctly
- actor: researcher processing a real physiological recording (ECG, EMG, PPG or RSP)
- input_artifact: a physiological recording (or simulated signal with known ground truth) passed to a NeuroKit signal-processing function
- operation: run a NeuroKit signal-processing function (emg_process, hrv_rsa, fractal_dfa, rsp_process, signal_power, signal_recompose, hrv, ...) on the recording
- observed_failure: the function crashes (IndexError/KeyError/AttributeError/TypeError) or returns a silently wrong numeric value (unit-dependent DFA exponent, negative RSA, 4x-shifted EMG filter, 99%-too-small phase durations)
- expected_output: correct numeric values (unit-invariant, computed on heart period, rate-aware filtering) and no crash
- affected_product: NeuroKit2 (neurokit2)
- version_or_environment: NeuroKit2 0.2.12-0.2.13 / dev @ f40486992, Python 3.11-3.13, NumPy 2.x

### 6513 AI — drive an AI agent / API reliably
- actor: developer calling an LLM API or driving an AI agent
- input_artifact: an LLM API call: a token-count request, or a Responses API stream carrying a function_call
- operation: invoke the API and consume its result (token count; streamed function-call completion)
- observed_failure: the result the caller receives is silently wrong or silently missing: a substituted tokenizer inflates the count (up to +108% on CJK), or the completion event for a function_call is never emitted so the caller cannot know the call finished
- expected_output: a result faithful to the model/API actually used: token count within 2% of the true tokenizer; exactly one completed chunk when response.output_item.done arrives, none when it does not
- affected_product: LLM API client / agent framework (AgentLab, langchain-openai)
- version_or_environment: AgentLab current main; langchain-openai 1.7.4, langchain-core 1.7.x, Python 3.14

### cd02 BIO — read and write biosignal files
- actor: researcher working with biosignal files
- input_artifact: a biosignal file: a WFDB record/annotation set, an EDF file, or a FIFF forward solution
- operation: read the file and write it back (round trip) with the same library
- observed_failure: the read or write crashes (OverflowError, HeaderSyntaxError, TypeError, IndexError) or the round trip loses/changes data (wrong checksums, lost subcortical source spaces, wrong defaults, split-file names the reader cannot find)
- expected_output: the file reads and writes back without crashing and without the data changing
- affected_product: biosignal file I/O libraries (wfdb-python, MNE-Python)
- version_or_environment: wfdb-python 4.1.2; MNE-Python 1.13.x; NumPy 2.2; Python 3.9-3.12

### e309 FIN — fetch market/financial data reliably
- actor: investor/researcher fetching market and financial data for a symbol
- input_artifact: a market/financial data request for a symbol (daily history, option chain, SEC company facts, Form 4 filings, news)
- operation: fetch the data through the library's fetcher (yfinance Ticker/download, openbb-sec/openbb-cboe fetchers)
- observed_failure: the fetcher returns wrong values (IV 500-2000%, valuations disagreeing with the source), silently missing values (a trading session absent, get_news [] on a 404), or leaks/corrupts resources under concurrent use (CLOSE_WAIT sockets, shared cache corruption, a cache that never caches)
- expected_output: complete, correct values for the requested symbol and session; missing data flagged explicitly; no socket or cache corruption under concurrent use
- affected_product: market/financial data fetchers (yfinance, openbb-sec, openbb-cboe)
- version_or_environment: yfinance 1.7.0-1.8.0; openbb 4.7.2 / openbb-sec 1.6.7 / openbb-cboe 2.0.0; Python 3.12-3.13

### 6513 AI — sample: LangChain #41708 streaming completion
- **Sample input (verbatim reproducer from the issue):**
  `langchain-openai 1.7.4`: feed
  `_convert_responses_chunk_to_generation_chunk` a
  `response.output_item.done` chunk whose item is a `function_call`
  (`name="echo"`, `arguments='{"text":"OK"}'`, `call_id="call_1"`,
  `id="fc_1"`, `output_index=0`), after `response.output_item.added`
  and the `response.function_call_arguments.delta` events.
- **Expected result:** exactly one completed generation chunk carrying
  the finished call (identity + complete arguments); the same sequence
  without the `done` event emits no completed chunk.
- **Independent support group (DIRECT only):** LangChain #41708
  (streaming completion) + AgentLab #340 (count_tokens silently
  substitutes the GPT-4 tokenizer; +108.3% Chinese, +18.5% Japanese,
  +11.7% English). Two orgs, two authors.
- **Unresolved status:** #41708 CLOSED in R02 (2026-11-05), resolution
  unverified from comments (closed != fixed); #340 OPEN. Neither
  link's fix status was re-checked live.
- **Matching reason:** both are the signature's failure — an LLM API
  call whose result reaches the caller silently wrong or silently
  incomplete — in two different client libraries.
- **Caveat (granularity):** #340 (tokenizer substitution) and #41708
  (streaming completion) are different failure mechanisms inside the
  signature's failure class. This theme survives ONLY under the
  failure-class grouping the brief itself uses ("tokenizer/streaming"
  as one side of the mandatory split). A stricter reader who splits
  tokenizer from streaming into two problems leaves each at 1 DIRECT
  link / 1 org, and the theme fails. R2-04 / QA may adopt the stricter
  reading; it is recorded here, not hidden.
