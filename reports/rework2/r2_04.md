## 1. The scoring rule (evidence-bound)

Old rule (R05): every qualifying theme scored exactly 70 = E20 + S20 + F15
+ G10 + L5. Review P1-01 showed F and L were unproven by the record's
own admission. New rule, implemented in `src/demand_radar/score.py`
(docstring carries the full rule) and `src/demand_radar/selection.py`:

- **E — from DIRECT_SAME_PAIN evidence only** (R2-03 `direct_only_counts`),
  for pains R2-03 assessed; unassessed pains keep the R03 org-group count.
  Adjacent / duplicate / out-of-scope links contribute nothing. Same
  E_MAP as before (0/1/2/3/4/5+ orgs → 0/10/15/20/25/30).
- **S — UNCHANGED in R2-04** (keyword-derived severity). P1-01 also
  questioned S=20 ("from a broad blocker keyword match, not a real loss
  measure"). It is recorded here as a residual limitation, NOT silently
  fixed: keeping S is conservative in the review's direction — even with
  S=20 retained, no theme reaches 70. If S were also zeroed, the scores
  would fall to 10 / 10 / 25 / 15 / 15. The conclusion does not depend
  on S.
- **F — 15 ONLY when `pain_points.workaround_status = 'DOCUMENTED'**
  (a real, verifiable workaround recorded). Otherwise 0 / UNKNOWN:
  - placeholder `'see linked issues'` → UNKNOWN, F=0. The placeholder
    is converted to NULL/UNKNOWN in the scoring path via the new
    `workaround_status` column (migration in `db.py::init_db`, idempotent
    backfill); the raw `current_workaround` text is NEVER overwritten —
    it stays in the DB for the diff (204 NULL, 17 `'see linked issues'`).
  - no workaround recorded (NULL) → UNKNOWN, F=0.
  - a paid/rate-limit keyword mention is NOT feasibility evidence → F=0.
  - In this dataset workaround_status is UNKNOWN for all 221 pains, so
    F=0 everywhere. F>0 is possible in future only with a documented
    workaround (test `test_documented_workaround_yields_f_points` proves
    the branch works).
- **G — 0 if any check does_solve=1; 0 if any UNKNOWN trail exists;**
  10 if ≥2 REAL (non-UNKNOWN) checks and none solves; 5 if exactly 1
  real check; 0 if no real check. (Old code awarded G=10 for ≥2 rows
  even when a row was an UNKNOWN trail — that defect is fixed.)
- **L — 0 always in this dataset.** No documented transfer/reuse
  evidence exists, and a component with no evidence behind it is 0,
  never a positive minimum. L>0 requires a documented reuse_evidence
  record; no schema for one exists yet, so no L point can be awarded
  honestly.
- **Cap-59** (total capped at 59 when <2 independent sources) is
  unchanged but is now unreachable at 1 org: the maximum reachable total
  with 1 DIRECT org is 55 (E10+S20+F15+G10+L0, even with a DOCUMENTED
  workaround). It stays as a safety net; the pure-function cap tests in
  `test_score.py` still cover it. Two older tests that asserted the
  defective F=15/L=5 totals were updated with reasons recorded in the
  test itself (`test_independence.py::test_cap59...`,
  `test_independence.py::test_migration...`,
  `test_cli.py::test_score_writes_ranking`).
- **Gate: 70, unchanged** (`selection.GATE_MIN_SCORE == 70`, pinned by
  test). The gate now also uses DIRECT-only orgs/authors/evidence and
  the DIRECT closed/open split for assessed pains.

## 4. The 6513 granularity decision (stated, not hidden)

R2-03 recorded 6513 as SURVIVING with a caveat: its two DIRECT links are
**different mechanisms** — AgentLab #340 (tokenizer silent substitution,
+108% CJK) vs LangChain #41708 (streaming missing completed event) — under
one "signature failure" class ("silently wrong or silently missing
result"). R2-03 grouped them by the failure-class rule and by the brief's
own mandatory split ("tokenizer/streaming" as one side).

**Decision adopted in R2-04: the STRICTER (mechanism-level) reading.**
The org gate exists to show the SAME demand appearing independently in two
places. A tokenizer-substitution report does not corroborate a
streaming-completion demand (different reproducer, different acceptance
test, different fix), and vice versa. Under the stricter reading each
mechanism stands at 1 DIRECT link / 1 org / 1 author, and 6513 fails the
org and author gates as well as the score gate.

**What changes if the stricter reading is adopted: nothing about
qualification, everything about the recorded reason and the future bar.**
Under the failure-class reading 6513 has DIRECT 2/2 orgs/2 authors and
new score 45 — still < 70, still NOT qualified (score alone fails it).
Under the stricter reading it additionally fails the org/author gates.
The gate CSV (`not_qualified_r2_04.csv`) shows the class-reading numbers
(n_orgs=2, n_authors=2, failure "score 45 < 70") because R2-03's
assessments were not edited (per task rule) and no mechanism split exists
in the data; this section records the stricter reading and its consequence:
for 6513 to ever re-qualify, new DIRECT evidence of the SAME mechanism in
a second org would be needed — not just another silent-failure report in
a different mechanism. R2-06/QA may adopt either reading; both give
NOT QUALIFIED for this stage.
