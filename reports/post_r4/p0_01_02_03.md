## 2. P0-01 — four terminal events, data after terminal, conflicts

`StreamingHandler` (`mvps/r1_a/validator.py`):

- Terminal events are now an explicit enumeration, verified against
  the OpenAI Python SDK event contract (openai-python main,
  `response_stream_event.py` — `ResponseCompletedEvent`,
  `ResponseFailedEvent`, `ResponseIncompleteEvent`,
  `ResponseErrorEvent`; the SDK's websocket example treats
  failed/incomplete as errors, never as success):
  `response.completed` → `completed`, `response.failed` → `failed`,
  `response.incomplete` → `incomplete`, `error` → `error`.
- The handler records the FIRST terminal event in `_terminal`
  (and keeps the event itself in `_terminal_event` so the reason can
  be explained). `response.failed` / `response.incomplete` /
  `error` are failure terminals — NEVER an "open" stream still in
  progress. `termination` now returns `completed` / `failed` /
  `incomplete` / `error` / `open` / `none`. The old
  `response_completed` property is kept (`_terminal == "completed"`)
  so the R4 completed-with-pending rule is unchanged.
- Data after ANY terminal event is an anomaly: kind
  `event_after_completed` after `response.completed` (the kind name
  the R4 contract tests assert — kept so those tests are untouched)
  and `event_after_terminal` after any other terminal. The event is
  still processed normally; the verdict fails via the anomaly.
- A second terminal event of a DIFFERENT kind is a
  `conflicting_terminal` anomaly and fails validation (a response
  ends exactly once; the first terminal wins and `termination` still
  reports it). A second terminal of the SAME kind is tolerated but
  recorded in `duplicate_terminals` (same precedent as duplicate done
  events) and mentioned in the detail — it does not fail on its own.

## 3. P0-02 — `validate_stream`: only a normal completion can pass

- `terminal_failed = termination in ("failed", "incomplete", "error")`
  is now a pass condition: a failure terminal always gives
  `passed=False`. The outcome is `"wrong-result"` — the OUTCOMES
  vocabulary has no `failed`/`incomplete` value, and the brief only
  requires `outcome != 'ok'` plus an explanation of which termination
  occurred. The detail names the terminal and its reason via
  `_terminal_reason`: `error` → the event's `code`/`message`;
  `incomplete` → `response.incomplete_details.reason` (e.g.
  `max_output_tokens` / `content_filter`); `failed` →
  `response.error` code/message when present.
- `response.completed` + pending still FAILS (unchanged);
  `response.completed` + complete still PASSES (unchanged).
- An `open` stream keeps its disclosed chunk-coherence semantics
  (a partial stream with no terminal signal can still pass on chunk
  integrity), but the detail now says so explicitly in BOTH cases:
  `"; stream still open (no terminal event) — request success not
  yet proven"`. The old wording `"(no response.completed)"` was
  replaced because there are now four terminal types; the R4
  contract test's `"still open"` assertion still holds.
- A failure terminal with NO calls at all (e.g. `[response.failed]`)
  is a failed response (`wrong-result`, `passed=False`), not
  `not-checked` — it IS a streaming event, so there is something to
  validate.

- Counting is automatic and was verified, not assumed: a
  failed-terminal streaming scenario returns outcome
  `wrong-result` / `passed=False` from `run_scenario`, and the app
  counts a check as passed only when `outcome == "ok" and passed`
  — so it lands in "failed", never "passed". No fixture was added
  (adding one would change the 22-check fixture counts), so the
  fixture sweep is unchanged: **9 passed, 13 failed, 0 not checked**
  of 22 checks, verified live through AppTest.
- The app banner (`mvps/r1_a/app.py`) now says, in the warning:
  "a stream with no terminal event is reported 'open': its chunks
  may be coherent, but the request's success is not yet proven — an

  response.failed, response.incomplete or an error event is a
  failure and never counts as passed, even when every call
