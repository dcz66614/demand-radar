## 1. R3-01 — StreamingHandler: true multi-call argument correlation

**File:** `mvps/r1_a/validator.py` (StreamingHandler + validate_stream).

**The defect (audit P1-01):** `_key_for()` checked `event.output_index`
before `event.item_id`, so a real Responses API delta carrying both
`item_id='fc_A'` and `output_index=0` was keyed by the string `"0"`,
matched no pending call, and was dropped — both calls completed with
empty arguments while `validate_stream` still said `ok`.

**Real protocol reference (fetched 2026-11-06, NOT guessed):**
- `openai-python/.../response_function_call_arguments_delta_event.py`:
  `delta: str`, `item_id: str` ("The ID of the output item that the
  function-call arguments delta is added to"), `output_index: int`,
  `sequence_number: int`.
- `openai-python/.../response_output_item_added_event.py`: `item`,
  `output_index: int`, `sequence_number: int`.
- `openai-python/.../lib/streaming/responses/_responses.py`: the SDK's
  own helper resolves deltas by `output_index` (`_get_output_item`)
  and raises on a content event for an unknown output index; it also
  raises on a duplicate output index. This handler records the same
  conditions as anomalies instead of raising, because a validator
  must report bad input, not crash on it.

**New design:**
- Canonical identity = the added item's `item.id`. Three separate
  namespace maps (`item.id`, `item.call_id`, `event.output_index`)
  each point at the canonical key. A delta/done carrying several keys
  must resolve through ALL of them to the SAME call; disagreement —
  including a key field naming a value that was never registered while
  another key resolves — is a `key_conflict` anomaly, fail-closed,
  never attributed to another call.
- Index-derived canonical keys are prefixed (`output_index:0`) so an
  index can never collide with a raw id/call_id string (e.g. id `"0"`).
- Keyless deltas (the recorded #41708 fixtures carry neither item_id
  nor output_index) are attributed to the single pending call ONLY
  when exactly one call is pending. With 0 or ≥2 pending they are
  recorded as `unknown_delta` / `ambiguous_delta` and dropped — never
  silently given to the most recently added call.
- Duplicate `sequence_number` deltas for the same call are dropped
  (`duplicate_sequence`); a delta for an already-completed call is
  dropped (`delta_after_done`); a re-added identity or a namespace
  value already bound to another call is recorded
  (`duplicate_added` / `key_conflict`).
- Done cross-validation: the done item's `arguments` are authoritative.
  When non-empty they must be valid JSON and must equal the
  accumulated deltas; a mismatch (`arguments_mismatch`) or non-JSON
  arguments (`invalid_arguments_json`) marks the completed chunk
  `arguments_valid=False` and records an anomaly. When the done item
  carries no arguments, the accumulated deltas stand; empty +
  empty is a legal no-argument call. Duplicate done still emits once
  (recorded in `duplicate_dones`, tolerated as in R2-05); done for a
  never-added call is an orphan (no completed emitted).
- `validate_stream` now checks completion count + correct association
  + argument integrity: emitted set == done set, no orphans, no
  anomalies, every completed chunk `arguments_valid`. A call added
  but never done does NOT fail (the handler correctly emitted
  nothing; the detail says how many calls are still pending — this
  preserves the existing `test_streaming_without_done_emits_none`
  behaviour). An event list with no streaming events at all returns
  `not-checked`; any other failure is `wrong-result`, never `ok`.

**Verification:**
- Independent test `test_parallel_stream_preserves_each_arguments_payload`
  GREEN; all pre-existing streaming tests GREEN (including the recorded
  #41708 replay, output-index-only keying, call_id keying, duplicate
  done, orphan done, partial done, and the 50-trial randomised
  interleaving from R2-01).
- 14 new contract tests in `tests/test_rework3_contract.py` (§R3-01):
  interleaved 3 calls (dual-key), same-index conflict, duplicate
  sequence, unknown item_id, keyless delta with 2 pending, delta
  after done, done-arguments mismatch, done-arguments invalid JSON,
  done final arguments without deltas, legal no-argument call, empty
  event list → not-checked, duplicate done, done-before-added.
- Fresh-seed randomised check (seed 20261106, differs from the
  suite's): 60/60 trials, 4 dual-key calls, random interleaving,

## 2. R3-02 — Factual content: expected_answer is actually compared

**File:** `mvps/r1_a/validator.py` (`check_factual_content`, `_validate_payload`).

**The defect (audit P1-02):** with only `expected_answer` supplied
(no keywords, no forbidden claims), `missing=[]` and
`present_forbidden=[]`, so ANY response returned `('ok', True,
'response content matches the expected answer ...')` without any
comparison — "The capital of France is London." passed against
"The capital of France is Paris.".

**New design — the three rules are separate checks:**
- `expected_answer`: ACTUALLY COMPARED as a normalized word-multiset
  match (case-, punctuation- and word-order-insensitive). Match →
  `ok`; anything else → `wrong-result`. A paraphrase is not verified,
  a contradiction is wrong, a refusal is wrong. Negation is caught
  because the word multiset differs ("Paris is NOT the capital" adds
  "not", drops "of"/"france"). Word-order-insensitivity is REQUIRED
  by the pre-existing R2-05 test
  `test_factual_content_matching_is_case_and_punctuation_insensitive`
  ("PARIS is the capital of France!" must pass against "The capital
  of France is Paris.") — so the check is a lexical multiset match,
  NOT a semantic verification, and the docstring + detail say so
  ("normalized word-multiset match"). Known limit, stated: word order
  is ignored.
- `expected_keywords`: a keyword rule ONLY. Keywords present with no
  expected_answer → `not-checked`, detail says "factual truth not
  checked — keyword match does not verify factual correctness".
  "Paris is NOT the capital" hitting keyword `paris` is therefore
  never claimed as verified factual correctness. Missing keyword →
  `wrong-result`.
- `forbidden_claims`: present → `wrong-result`; absent on its own →
  `not-checked` (absence of a forbidden claim does not verify the
  answer).
- Nothing supplied → `not-checked` (unchanged).
- `_validate_payload` now propagates a `not-checked` factual result
  instead of swallowing it into `"ok"` — a scenario must not claim a
  validation that never happened. (No fixture hits this path: both
  factual fixtures supply `expected_answer`.)

**Verification:**
- Independent test
  `test_expected_answer_only_must_not_mark_contradiction_as_correct`
  GREEN.
- 11 new contract tests (§R3-02): known correct, opposite answer,
  refusal, negation sentence, negation with keyword-only (not-checked,
  never claimed correct), keyword missing, only expected_answer
  (pass + fail), only forbidden_claims (not-checked), forbidden
  present, no rules (not-checked), word-order variant (passes, detail
  says lexical only).
- Pre-existing factual tests all GREEN (false/true OpenRouter
  fixtures, case-insensitivity, no-answer not-checked).

## 3. R3-03 — Schema fail-closed

**File:** `mvps/r1_a/validator.py` (`_matches_type`, `_validate_payload`).

**The defects (audit P2-01, P2-02):** unknown type names returned
`True` (fail-open: `{"n": "integer"}` with `{"n": true}` passed
because only `int` was recognised); `float('nan')` satisfied
`float`.

**New design:**
- Supported type names are an explicit, documented contract:
  JSON Schema standard names (`integer`, `number`, `string`,
  `boolean`, `array`, `object`, `null`) plus the short names the R06
  fixtures already use (`int`, `float`, `str`, `bool`, `list`,
  `dict`). `integer`/`int` = Python int, never bool, never float
  (2.0 does NOT satisfy "integer" here, by contract — a float is
  not an integer, even though JSON Schema would allow a
  zero-fraction number). `number`/`float` = int or float, never bool,
  and always FINITE. `null` = only None.
- Any other type name raises `SchemaConfigError` (a readable
  configuration error); `_validate_payload` catches it and returns
  `("not-checked", False, "schema configuration error: ...")` —
  fail-closed, never a silent pass. The same applies to nested
  specs: unknown types inside `object.properties` / `array.items`
  raise, and a dict spec without a `type` field raises.
- Non-finite floats (NaN, +inf, −inf) never satisfy `float`/`number`
  — they are not valid JSON numbers. (Huge ints are finite by
  definition; `math.isfinite` is only called on floats because it
  raises OverflowError on huge ints.)
- bool never satisfies `number`/`integer`/`int`/`float` (as in R2-01).

**Verification:**
- Independent tests `test_unsupported_schema_type_must_not_silently_pass`
  and `test_nonfinite_float_is_not_valid_json_number` GREEN.
- 7 new contract tests (§R3-03, incl. parametrised int/integer and
  number/float): unknown type (top-level and nested), NaN/±Inf
  (top-level and nested), bool vs number/integer, all 7 standard
  JSON Schema names, nested non-finite rejection.
- Pre-existing R2-01 schema tests all GREEN.
