## 1. R4-01 — strict JSON parsing (audit P1-A)

**The defect.** R3-03's NaN/Inf fail-closed only applied to Python
numbers already checked against a schema. The raw JSON paths used
bare `json.loads`, which ACCEPTS `NaN` / `Infinity` / `-Infinity`:
`_validate_payload({}, {'raw': '{"n":NaN}'})` returned
`('ok', True, 'response valid')`, and `validate_stream` passed a
function call whose arguments were `{"n":NaN}`.

**The fix.** One strict parser, `_parse_strict_json`, used by every
path that claims a string is "valid JSON":

- `json.loads(text, parse_constant=...)` where the hook raises
  `ValueError` on `NaN` / `Infinity` / `-Infinity`. The hook is only
  called for BARE constants — the string `"NaN"` inside a JSON string
  value is legal text and is preserved. No regex is used anywhere,
  so string contents are never touched.
- After parsing, `_check_finite` walks the value recursively and
  rejects any non-finite float — `json.loads('1e999')` succeeds and
  yields `inf`, so the parse alone is not enough; the walk catches
  it at any nesting depth. Ints are finite by definition and are
  never checked.

Call sites (all now catch `ValueError`, which covers both
`JSONDecodeError` and the strict rejections):
- `_validate_payload` raw body → `("wrong-result", False, ...)`
- `_handle_done` final arguments AND accumulated deltas → chunk
  `arguments_valid=False` + `invalid_arguments_json` anomaly
- `load_scenarios` (a fixture file with NaN is not a valid scenario
  file — raises `ValueError`)
- `mvps/r1_a/app.py` uploaded-scenario path (same claim, same
  parser; the existing `except (ValueError, ...)` already catches it)

Out of scope, noted: `mvps/r1_b/signalcheck.py:502` and
`src/demand_radar/ingest.py:17` also call `json.loads`, but they load
local fixture/ingest lines, not validator payloads — the brief names
the validator paths, and the audit's P1-A is about the validator.
Recorded as a residual in the final report.

## 2. R4-02 — not-checked is not a pass (audit P1-B)

**The defect.** With only `expected_keywords`, a response that
CONTAINS the keyword but contradicts the claim
(`"Paris is NOT the capital of France."`) returned
`outcome='not-checked', passed=True`, and the R1-A app counted it
with `sum(r.passed for r in results)` — an unverified claim inflated
the UI pass rate, contradicting the report's "not-checked does not
claim factual verification".

**The fix.**
- `check_factual_content`: all three `"not-checked"` returns now
  carry `passed=False` (no-rules, keyword-present,
  forbidden-absent). The docstring states the rule: not-checked is
  not a verified pass. `_validate_payload` already propagated the
  pair, so `run_step` now returns `passed=False` for these cases.
- `mvps/r1_a/app.py`: three separate counts — verified passed
  (`outcome == "ok" and passed`), failed (everything else except
  not-checked), and not-checked (its own count). The summary line
  reads "**X passed, Y failed, Z not checked** of N checks". The
  Outcome filter gained a "not-checked" option; "fail" now means a
  real failure (not passed AND outcome != 'not-checked').
- The brief's "best" option (independent `rule_matched` /
  `factual_verified` fields) was NOT taken: the `outcome` field
  already IS the separate state, and adding fields to `CallResult`
  would ripple through `export_csv` and every consumer for no extra
  information. The minimal change is the honest one here, and it is
  what the audit test requires (`r.passed is False`).

**Ordinary tests updated (allowed by the brief; frozen 9 untouched):**
- `tests/test_rework3_contract.py` — `test_r3_02_only_forbidden_claims_is_not_checked`
  and `test_r3_02_no_rules_is_not_checked`: `passed` → `not passed`.
- `mvps/r1_a/tests/test_real_paths.py` —
  `test_factual_content_without_expected_answer_is_not_checked`:
  `passed` → `not passed`.
- No fixture step is keyword-only (the two factual fixture steps
  both supply `expected_answer`), so the 22-check fixture counts and
  the AppTest filter counts are unchanged (verified: AppTest 3/3).

## 3. R4-03 — stream termination consistency (audit P2-C)

**The defect.** `[added(function_call), response.completed]` — the
response ended with the call never done — returned
`{'outcome': 'ok', 'passed': True, 'emitted': 0}` while its own
detail said "1 call(s) added but never done".

**The fix.**
- `StreamingHandler` records `response.completed` as the terminal
  signal (`_response_completed`, property `response_completed`).
  Any streaming event (added / delta / done) arriving AFTER it is
  recorded as an `event_after_completed` anomaly — the response had
  already ended. (Hardening within the same rule: a done after
  completed is a protocol violation, not a late event.)
- `validate_stream` returns a `termination` field:
  `'completed'` (a `response.completed` was seen), `'open'` (streaming
  events seen, no completion signal), `'none'` (no streaming events).
- `response.completed` with any pending call → `wrong-result`,
  `passed=False`, detail "response completed with N call(s) still
  pending (function_call never done)".
- A partial stream with NO completion signal keeps its previous
  verdict (the added-but-never-done call emits nothing — the
  `test_streaming_without_done_emits_none` behaviour is preserved
  byte-for-byte), but its `termination` is `'open'` and its detail
  says "stream still open (no response.completed)" — an unfinished
  stream is never silently treated as finished.
